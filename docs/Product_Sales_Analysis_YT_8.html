One giant table?
Or two tables that talk to each other?

Every electronics store — ours included — has to track two very different things: what we sell, and what customers bought. How we store that decides whether our database is a mess or a machine.

So, let's go a little deeper and understand which approach is better, and why.

Option 1

Store everything in one giant table

Every sale stores the product name directly, right alongside the sale details.

Problem 1

Storage & duplication

The text "iPhone 16" gets written again for every single sale — 10,000 sales means 10,000 repeated copies of the same string.

Problem 2

Data inconsistency

Five employees, five spellings. "How many iPhone 16s did we sell?" suddenly has no clean answer.

Problem 3

Painful renames

Rename one product and you may need to update 100,000+ rows — and risk missing some of them.

The Fix

Give every product an ID.

Instead of repeating the name everywhere, we write the ID everywhere — and store the name exactly once.

200
→
iPhone 16

Now the sales table stores product_id = 200 instead of typing the name out every time.

Option 2

Two tables, connected by an ID

The Product table owns product info. The Sales table owns sale info. A shared product_id links them.

Rename 200 from "iPhone 16" to "Apple iPhone 16"? Update one row in Product. The Sales table never has to change.

The Big Idea

Separate data by what it represents.

This is the core instinct behind database normalization: store shared facts once, and reference them everywhere else.

📦

Less duplication

One name, stored once — not once per sale.

✅

Better consistency

One ID always means one exact product.

⚡

Easier updates

Change a name in one place, done everywhere.

🗂️

Better organization

Each table has one clear job.
